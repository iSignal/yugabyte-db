# Learning: master sys_catalog tablet structure & how it could be bootstrapped

Source: code reading pass 1 (2026-06-19). All paths under
`/net/dev-server-sanketh-3/share/code/yugabyte-db`.

## 1. The sys_catalog tablet: one tablet, one RocksDB, two kinds of content

- Single tablet, hardcoded all-zeros id:
  `kSysCatalogTabletId = "00000000000000000000000000000000"`
  (`src/yb/master/sys_catalog_constants.h:39-47`).
- The tablet's *primary* table is `sys.catalog`, a fixed 3-column schema built in
  `SysCatalogTable::BuildTableSchema` (`src/yb/master/sys_catalog.cc:808-814`):
  key `(entry_type INT8, entry_id BINARY)`, value `metadata BINARY`.
- Two distinct kinds of content live in the *same* RocksDB:
  1. **DocDB metadata rows** — stored in the `sys.catalog` table as
     `(entry_type, entry_id) -> metadata(serialized PB)`. `entry_type` is the
     `SysRowEntryType` enum (`src/yb/master/master_types.proto:31-57`:
     `TABLE=1, TABLET=2, CLUSTER_CONFIG=3, NAMESPACE=4, UDTYPE=5, ROLE=6,
     SNAPSHOT=7, ...`). On-disk row = `SysRowEntry{type,id,data}`
     (`catalog_entity_info.proto:574-591`). This is the stuff we do NOT want on
     tservers.
  2. **PG catalog tables** (pg_class, pg_attribute, ...) — each is a *real,
     distinct DocDB table* co-located in the same tablet. This is the stuff we
     DO want.

## 2. How PG catalog tables are represented (the payload to replicate)

- Each PG catalog table is a real DocDB table with its own `table_id`. The
  table_id encodes `(database_oid, table_oid)`:
  `GetPgsqlTableId(database_oid, table_oid)` packs db OID into bytes 0-3 and
  table OID into bytes 4-7 of a UUID (`src/yb/common/entity_ids.cc:125-139`,
  `src/yb/common/pg_types.h:50`). So **each YSQL database has its own
  pg_class/pg_attribute/... distinguished by db OID in the table_id**, all
  co-located in the one sys_catalog tablet.
- Co-location key: each table's rows are prefixed in the DocKey by its
  `cotable_id` (the table_id UUID) — `src/yb/dockv/doc_key.h:114-124,153-158,410`
  (`DocKey(const Uuid& cotable_id, ...)`, `DocKeyEncoderAfterTableIdStep::CotableId`).
  This UUID prefix is how many logical PG tables share one RocksDB without key
  collisions.
- Table schemas live in the tablet's `RaftGroupMetadata`: one `KvStoreInfo`
  (one RocksDB) with `TableInfoMap tables` keyed by table_id plus a
  `primary_table_id` (= `sys.catalog`). See `src/yb/tablet/tablet_metadata.h:277-358`;
  persisted via `KvStoreInfoPB.tables[]` of `TableInfoPB{table_id, schema,
  schema_version, ...}` (`src/yb/tablet/metadata.proto`).
- Registration: when a YSQL system table is created (during initdb, and again
  per CREATE DATABASE), the master issues a `ChangeMetadataRequestPB` targeting
  `kSysCatalogTabletId` and then `SyncReplicateChangeMetadataOperation(...)`,
  registering the schema into the tablet metadata
  (`src/yb/master/catalog_manager.cc:4005-4036`).
- Row population for a new DB: `SysCatalogTable::CopyPgsqlTables`
  (`src/yb/master/sys_catalog.cc:1972-2014`) iterates rows of each source PG
  table via `tablet->NewRowIterator(projection, {}, source_table_id)` and upserts
  into the target db's co-located copies with `InsertPgsqlTableRow`. **This is an
  existing in-tablet "copy the PG catalog" primitive** (used by CREATE DATABASE
  to clone template1).

## 3. Iterating sys_catalog rows

`src/yb/master/sys_catalog_writer.cc`:
- `ReadNextSysCatalogRow` (`:62`) — extracts `(entry_type, entry_id, metadata)`
  by column id, invokes a callback with `(entry_id.binary_value(),
  metadata.binary_value())`.
- `EnumerateSysCatalog` (`:243`) — scans one entry_type via a `DocQLScanSpec`
  with `QL_OP_EQUAL` on `entry_type`, iterating a `DocRowwiseIterator`.
- `EnumerateAllSysCatalogEntries` (`:278`) — all entry types.
- Write side for DocDB-metadata rows: `FillSysCatalogWriteRequest` (`:193-230`).
- Write side for PG catalog rows is different: `InsertPgsqlTableRow` /
  `DeleteYsqlTableRow` (`:131-191`) build `pgsql_write_batch` entries
  (`YQL_CLIENT_PGSQL`, `PGSQL_UPSERT/INSERT/DELETE`) targeting a co-located
  table_id with range key + column values.

## 4. The initial sys_catalog snapshot (initdb seeding) — a reusable primitive

- Generated by `src/yb/yql/pgwrapper/create_initial_sys_catalog_snapshot.cc`
  (a test harness that boots a master with `--create_initial_sys_catalog_snapshot`,
  `--master_auto_run_initdb`, `--initial_sys_catalog_snapshot_path=<dest>`).
  **initdb runs in-process in the master's embedded PG, writing directly into the
  master's sys_catalog tablet** (NOT on a tserver, NOT via Raft from elsewhere).
- On-disk format (`src/yb/master/sys_catalog_initialization.cc:63-66`):
  ```
  <snapshot_path>/
    rocksdb/                          # a RocksDB checkpoint (SST + MANIFEST + CURRENT)
    exported_tablet_metadata_changes  # protobuf: ExportedTabletMetadataChanges
  ```
  Confirmed present in this checkout under
  `build/.../share/initial_sys_catalog_snapshot/`.
- Write (`sys_catalog_initialization.cc:82-112`): flush tablet,
  `snapshots().CreateCheckpoint(<dest>/rocksdb)`, then dump all accumulated
  `ChangeMetadataRequestPB`s (collected during initdb at
  `catalog_manager.cc:4034-4035`) into the protobuf file.
- Restore (`sys_catalog_initialization.cc:118-162`, two phases):
  1. `SnapshotOperation` with `RESTORE_ON_TABLET` and
     `snapshot_dir_override = <path>/rocksdb`, submitted to the sys_catalog
     tablet peer. The actual data import is `TabletSnapshots::RestoreCheckpoint`
     (`src/yb/tablet/tablet_snapshots.cc:508-545`): shut down the live RocksDB,
     delete its dir, **`CopyDirectory(..., CopyOption::kUseHardLinks, ...)`** the
     snapshot SSTs into the tablet RocksDB dir, reopen. A *filesystem* operation,
     not a Raft replay.
  2. Replay each exported `ChangeMetadataRequestPB` via
     `tablet::SyncReplicateChangeMetadataOperation(...)` to re-register every PG
     table's schema into `RaftGroupMetadata`.
- **Reusability for a tserver-local tablet: high.** Both restore primitives
  (hard-link SSTs; replay ChangeMetadata) operate on a `TabletPeer`/
  `RaftGroupMetadata` and do **not** require a running master or a multi-node
  Raft group. They would work on any local TabletPeer a tserver opens.
- **Caveat:** the static `share/initial_sys_catalog_snapshot` contains only
  template0/template1's catalog. Per-user-database pg_class/... copies
  (distinguished by db OID in table_id) are created lazily later via
  `CopyPgsqlTables`. Seeding a tserver with the *live, full* catalog requires a
  *live checkpoint* of the master sys_catalog tablet (`CreateCheckpoint`) plus the
  corresponding ChangeMetadata set — not the static file.
- **Caveat:** SSTs alone are insufficient. The `exported_tablet_metadata_changes`
  / `KvStoreInfoPB.tables[]` registry is what tells the tablet the cotable
  schemas; without it the tablet cannot interpret the rows.

## 5. Creating a tablet on a tserver, incl. standalone single-replica

- Standard path: `TSTabletManager::CreateNewTablet`
  (`src/yb/tserver/ts_tablet_manager.cc:999-1065`): `RaftGroupMetadata::CreateNew(...)`
  + `ConsensusMetadata::Create(..., config, ...)` + `CreateAndRegisterTabletPeer`
  + `OpenTablet`. The `RaftConfigPB config` argument fully determines membership.
- **Single-replica / local-only tablet has direct precedent:**
  - The master's own sys_catalog is created this way with a *single-peer*
    `RaftConfigPB` in the single-master case (`SysCatalogTable::CreateNew`,
    `sys_catalog.cc:354-392`). A config containing only the local peer yields a
    standalone single-node Raft group that self-elects leader immediately —
    exactly the shape wanted for a tserver-local copy.
  - `OpenTablet` (`ts_tablet_manager.cc:2117+`) just loads the persisted
    single-peer `ConsensusMetadata` and bootstraps; no multi-node requirement.
- **Closest template for "stand up a fresh local tablet seeded from existing
  RocksDB files":** the clone path `TSTabletManager::DoCloneTablet`
  (`ts_tablet_manager.cc:1486-1538`): builds a new `RaftGroupMetadata::CreateNew`,
  **hard-links the source snapshot's SST files** into the target
  (`CopyDirectory(..., kUseHardLinks, ...)`, `:1520`), sets `TABLET_DATA_READY`,
  flushes metadata, `CreatePeerAndOpenTablet`. Same hard-link mechanism as the
  initial-snapshot restore.
- Other tserver "special" tablets (transaction status, cdc_state, sequences_data,
  pg_auto_analyze, metrics snapshotter) are all *normal master-created,
  RAFT-replicated* tables, NOT standalone local tablets. The only genuine
  precedent for a single-replica standalone tablet is the master sys_catalog
  itself (and the clone path).

## Implications for the design

- **Bootstrap should be a checkpoint-copy seed**, modeled on
  `DoCloneTablet` / snapshot-restore (hard-link SSTs + replay ChangeMetadata),
  invoked out-of-band — NOT remote bootstrap (see
  [[learning-remote-bootstrap-and-read-replica]]).
- The seed source must be a *live* checkpoint of the master sys_catalog (to get
  all per-db catalogs), or built incrementally from `CopyPgsqlTables`-style reads.
- We get the whole tablet's RocksDB if we checkpoint it; the DocDB-metadata rows
  (`sys.catalog` table) come along unless we filter. We could either (a) tolerate
  the extra `sys.catalog` rows on tservers, or (b) post-filter to keep only the
  PG cotables. The cotable_id prefix makes PG-table data cleanly identifiable.
