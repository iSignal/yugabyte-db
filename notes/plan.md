Tserver-local docdb copy of catalog



---------

**Goal**: We want to have all tservers maintain a copy of the PG catalog that is stored in the sys catalog tablet on master
so that we can redirect all catalog lookups for catcache / relcache to this copy. The copy may not
be transactionally consistent with master but it needs to have changes as of the catalog version known
to this tserver at least.

--------

**Prior context of current state of code prior to this plan**:

1. All DDL except a few rare ones like create temp table increment a catalog version in the same
txn as their changes. When invalidation messages are enabled, the DDL commit also includes a list
of relcache/catcache entries that this DDL invalidates. The DDL uses an autonomous transaction which is
different from the regular transaction. Only when txn DDL / object locking is enabled, do DDL use the same
txn as the regular user txn.
2. Master propagates catalog versions in heartbeats and, when object locks are enabled, on global
lock releases from all DDL. Tservers receive heartbeats by default every 1 sec and set the latest version into shared memory.
3. PG backends use a catalog version from master to init themselves, then check the shared mem catalog version from tserver every txn/statement boundary. If they see a new version, they update to the new
version by applying invalidation messages (YbRefreshCache). As a result of steps 1-3, a DDL that changes
entries may take up to a heartbeat to propagate to backends.
4. PG backends support a feature called preloading. When additional preload gflags are enabled, they
fetch certain catalog tables on startup and use YbFillCaches to prepopulate all known entries and also
build relcache entries for all known relations. On later updates to catalog version, they apply invalidation
messages just like non preloading cases. Preload requests go through tserver response cache and are
cached there. This feature is intended to reduce cache miss latency to a remote region master.
5. When object locks are enabled, PG backends can apply inval msgs mid-statement during AcceptInvalidationMessages after each lock acquire potentially.
6. PG backends use a relcache init file to bootstrap relcache entries for catalog tables. This file has
the catalog version in it. In the non preloading case, if PG backends don't find this file or need to
rebuild it on a catalog version change, they trigger a separate relcache init conn to build it. This relcache
init conn performs preloading even if preloading is not enabled by gflags and uses the response cache to
do so.
7. General preloading which goes through response cache uses the serialized rpc request (minus a few fields) as the cache key for lookup. Multiple concurrent requests which hit the response cache result in only one
request to the master and others are served from this response when it arrives.
8. A catalog cache miss goes to master and reads catalog tables as of latest time, so it may see changes
outside its catalog version. Certain tests rely on this expectation but users do not. The minimum expectation
is that catalog cache misses at least reflect the changes as of that catalog version.
9. Clarification to point 3 : Though, in general, DDLs may not be visible to backends for a heartbeat delay, there are some special cases today
9.1 On the same tserver, a DDL sometimes increments catalog version locally in shared mem so it is visible
to backends on the same tserver faster. This is only done if no other DDL have incremented catalog version between its start and the commit.
9.2 When a DDL also has docdb changes, other backends may notice docdb schema version increments and retry
schema version mismatches by fetching latest catalog version, applying it and retrying the statement. Code lives in postgres.c.

10.Master today has a sys catalog that is populated seeded from a copy generated from initdb. initdb is
generated by a unit test named generate_initial_sys_catalog or similar (see create_initial_sys_catalog_snapshot)
Master sys catalog has various kinds of entries, some of which are internal docdb table/tablet state while
some are PG catalog entries. The SysCatalogEntryPB or similar named protos describe these formats.

-----------

**Rough outline of design**

Flag exists gating this feature. enable_local_tserver_catalog

1. A tablet is created on each tserver when flag is enabled. The intent of this tablet is to have
all PG catalog tables for all databases as well as shared catalog tables.
2. Key decision TBD: How is the tablet initially populated from syscatalog?
2.1 We could use some form of remote bootstrap but this option only works for members of same RAFT
groups, I think. Secondly, this means we also get all other entries of sys catalog.
2.2 We might be able to initialize this tablet similar to how master initializes at initdb time prior
to any user commands being run.
2.3 Some custom bootstrap similar to ReadNextSysCatalogRow in sys_catalog_writer.cc or Read RPCs to master
3. Once the tablet is initialized, it has to be kept up to date with updates on master.
3.1 Simplest option would be to read
master WAL entries for PG catalog changes and applying them. One prior art for this is cdcsdk_virtual_wal
(search for GetNextRecordToBeShipped/DeterminePubRefreshFromMasterRecord and master sys catalog table id) which also does the same.
We could have a poller on each tserver (similar to xcluster poller or CDC poller) which polls sys catalog every 100 ms via GetChanges
and applies changes locally. Note that these are WAL level changes, which may be individual writes or txn commits etc.
We would also get intents for the writes as DDL is written in txns, so those intents would need to be somehow applied to our local tablet.
This may mean that our local tablet has both intents and regulardb.
3.2 A different option would be to establish this tablet as a first class read replica of the master sys catalog. One question here
is whether this would scale to a 1000 tservers and whether we can maintain that size of read replicas in a RAFT group. But in such a case
remote bootstrap would probably work cleanly.
4. When tserver receives a notification of new catalog version from master, it has to ensure that all
writes corresponding to those DDL writes to sys catalog are caught up on this local tserver tablet.
4.1. To do this, one option is for the tail_sys_catalog mechanism in (3) to be aware of the hybrid time it is definitively
caught up to and expect to know the hybrid time of the latest catalog version write the tserver is receiving. The hybrid
time of the catalog version write would be derived on master by looking at the hybrid time of the pg_yb_invalidation_messages table
which has a primary key (db_oid, version).
4.2 Another option is to be aware of the safe time on master that we are caught up to when we poll for WAL entries and assure
ourselves that our last poll has caught up to the last time the master read this catalog version.
4.3 Today master informs tserver of new catalog versions via heartbeat or ReleaseObjectLocks API after DDL commit. Another
option is that the tserver ensures that its local tablet is caught up to the version reported by these methods by reading
the catalog version locally and only then propagating this version to PG shared mem. This may mean that a ReleaseObjectLocks
call is not ack'd until the tserver sees the same version locally.
4.4 Some other option involving the WAL LSN or WAL opid or WAL op write time (not the txn hybrid time).
5. We have more complex decisions like how is this tablet sync'd to master if it is network partitioned for a long time. We
could postpone such discussions by assuming master retains WAL for 1 day and no tserver is partitioned for that long. But if we
could figure out how to remote bootstrap either through the read replica approach or even in the WAL GetChanges poll.
6. Once we have all these pieces, we need to then be able to redirect catalog cache misses in catcache.c or relcache.c to this tablet. Note
that this tablet is not transactionally consistent with master, so we may not be able to redirect all reads even from DDLs which are currently
writing to sys catalog to this tablet but pure reads like catalog cache misses could be redirected. Operations like select * from pg_class also
could be redirected if we can detect we are not inside a txn block that has written to sys catalog (which is very rare outside of DDL).

--- Reframing after pass 1 ---
The hard parts are BOOTSTRAP (#2) and UPDATE (#3). Two of the plan's worries turn
out to be much easier than feared, and two of the candidate mechanisms are dead:
  * GOOD: the intents worry (#3.1) dissolves IF we use the CDCSDK *logical* format
    (committed, decoded, per-catalog-table rows) instead of the xCluster *raw*
    format (raw KV incl. intents). With CDCSDK the local tablet needs NO intentsdb
    and NO transaction-apply machinery.
  * GOOD: #4 (version <-> hybrid time) is essentially solved. The catalog-version
    bump and the pg_yb_invalidation_messages insert for (db_oid, V) are one CTE
    statement in the DDL txn => one commit HT. So the DocDB write_time of that
    inval row IS V's commit HT (projectable, no schema change). And there is
    already a synchronous gating seam (ReleaseObjectLocks) to block version
    exposure until the local copy catches up.
  * DEAD (at 1000-tserver scale): remote bootstrap as an ongoing sync mechanism,
    and read-replica/non-voter membership. Both require RAFT membership in the
    sys_catalog group, whose config is hardwired to the masters; leader fan-out is
    O(N peers). See learning-remote-bootstrap-and-read-replica.md.
=> Emerging shape: out-of-consensus. Checkpoint-copy bootstrap + CDCSDK pull
   poller + write_time-anchored version gate + DoPerform read redirect.

--- Detail on the sys_catalog data model (prerequisite for #1, #2, #6) ---
* sys_catalog = ONE tablet (kSysCatalogTabletId = "0"*32), ONE RocksDB, holding:
  (a) DocDB metadata rows in the sys.catalog table: key (entry_type, entry_id) ->
      metadata PB (table/tablet/namespace/role/...). NOT wanted on tservers.
  (b) PG catalog tables: each a real co-located DocDB table, one per
      (db_oid, table_oid); table_id packs both; rows prefixed by cotable_id UUID
      in the DocKey. THIS is the payload to replicate.
* PG-table schemas live in RaftGroupMetadata (KvStoreInfoPB.tables[]). SST data is
  useless without this schema registry — any bootstrap/update must carry schemas.
* cotable_id prefix means PG-table data is cleanly identifiable / separable from
  the sys.catalog metadata rows.

--- #1 Tablet creation on the tserver ---
* Single-replica, self-leading local tablet IS supported and has precedent: the
  master's own sys_catalog is exactly this in single-master mode (CreateNew with a
  single-peer RaftConfigPB). OpenTablet just loads the single-peer consensus meta.
* Closest template for "fresh local tablet seeded from existing SSTs":
  TSTabletManager::DoCloneTablet (hard-links source SSTs into a new
  RaftGroupMetadata::CreateNew, sets TABLET_DATA_READY, opens).
* TENTATIVE: create a standalone single-peer local tablet per tserver, seeded by
  checkpoint copy (see #2), NOT a member of any cross-node RAFT group.

--- #2 Initial population (the first hard decision) ---
* 2.1 Remote bootstrap: RULED OUT as the mechanism. RBS requires the target to
  join the sys_catalog RAFT config (== masters), copies the WHOLE tablet (no
  sub-table scoping), and doesn't scale. (A one-time RBS-style seed of an
  *independent* tablet would need entirely new out-of-band plumbing anyway.)
* 2.2 initdb-time init: the static share/initial_sys_catalog_snapshot only has
  template0/template1; a running cluster's per-user-DB catalogs are created lazily
  via CopyPgsqlTables. So the static snapshot is insufficient for a live cluster.
  BUT the snapshot *restore primitives* are reusable: hard-link SSTs + replay
  ChangeMetadata, both on a plain TabletPeer with no master/Raft.
* 2.3 Custom bootstrap: feasible. Two sub-options to evaluate next pass:
  (A) LIVE CHECKPOINT COPY: master takes a live CreateCheckpoint of its
      sys_catalog tablet + exports the ChangeMetadata/KvStoreInfo schema set;
      tserver hard-links/copies SSTs into a fresh local tablet (DoCloneTablet
      shape). Open: how to fetch the checkpoint without RAFT membership (a custom
      RPC that streams the checkpoint files — reuse the remote_bootstrap file
      transfer service but decoupled from config membership?), and how to filter
      out the non-PG sys.catalog rows (or tolerate them).
  (B) ROW-LEVEL COPY via reads: CopyPgsqlTables-style iteration of all PG catalog
      tables read from master into the local tablet. Cleaner separation (only PG
      data), but slower and needs a consistent read snapshot to hand off to the
      CDC poller's start checkpoint.
* TENTATIVE lean: (A) live checkpoint copy for speed, decoupled from RAFT
  membership via a custom file-streaming RPC; revisit filtering of sys.catalog
  rows. Must hand the poller a start point (OpId/hybrid time) consistent with the
  checkpoint.

--- #3 Keeping the local tablet up to date (the second hard decision) ---
* 3.1 WAL/GetChanges poller: STRONGLY FAVORED, and prior art exists. The master
  already runs a CDC service; cdcsdk_virtual_wal already polls sys_catalog and
  decodes per-catalog-table rows for the publication-refresh feature.
  - Use CDCSDK logical format (committed, commit-time-ordered, decoded rows). NOT
    xCluster raw format. This is what makes "no intents on the local tablet" true.
  - Poller modeled on XClusterPoller (self-rescheduling, ~100ms idle delay, tracks
    op_id checkpoint + safe_hybrid_time, advances checkpoint only after local apply).
  - Gaps to close (design work, not blockers):
      * "streamable catalog tables" today = ~3 tables (pg_class, pg_publication_rel,
        pg_replication_origin). Must generalize to ALL catalog + shared tables,
        ALL databases.
      * DDL / schema-version records: new cotables (CREATE TABLE/INDEX in catalog
        sense), new columns, CREATE/DROP DATABASE -> the local tablet must learn
        new table schemas (ChangeMetadata-equivalent) before applying their rows.
      * Per-db semantics and the new-database case.
* 3.2 Read replica of master sys_catalog: RULED OUT (scale + master-identity
  coupling; see learning-remote-bootstrap-and-read-replica.md).
* TENTATIVE: 3.1 CDCSDK logical poller.

--- #4 Ensuring the local copy is caught up to a reported version (LARGELY SOLVED) ---
* Anchor: write_time of the pg_yb_invalidation_messages row for (db_oid, V) == V's
  DDL commit HT (one CTE stmt in the DDL txn). Surface it by extending the master's
  inval-message read to project per-row write_time (PrimitiveValue::GetWriteTime
  exists; no schema change).
* 4.1 (HT of catalog version write): YES, via the inval-row write_time above.
  This is cleaner than re-deriving from the version table.
* 4.2 (poll safe time): complementary — the poller's safe_hybrid_time tells the
  tserver the local copy reflects all commits <= that time. Caught-up-to-V test =
  "applied the row writing V" AND "safe_hybrid_time >= V's commit_HT".
* 4.3 (gate version propagation): YES. ReleaseObjectLocks is a synchronous
  per-tserver RPC that already does a clock wait (WaitToApplyIfNecessary ->
  WaitUntil) before applying the version and ack'ing. Insert "wait until local
  tablet safe time >= V's commit_HT" between that wait and SetYsqlDBCatalogVersions.
  The heartbeat path (1s, async) needs an analogous gate before writing the new
  version into shared memory.
* 4.4 (WAL LSN/opid alternatives): not needed; HT anchor + safe time suffice.
* TENTATIVE: attach (db_oid, V, commit_HT) to ReleaseObjectLocks (and heartbeat);
  gate shm version update on local safe time >= commit_HT.

--- #5 Long partition / re-sync ---
* Leader WAL GC does NOT pin on slow non-voters, but CDC retention barriers DO pin
  the master sys_catalog WAL/intents/history while a stream is active
  (CDCMasterBgTask). So retention is governed by the slowest active CDC stream, not
  a flat 1-day assumption. Design the retention window deliberately.
* If a tserver falls outside the retention window: re-seed via the bootstrap path
  (#2A live checkpoint copy) and restart the poller from the new checkpoint point.
* OPEN: per-stream retention cost on master with N tservers each holding a barrier;
  whether to use one shared stream vs. per-tserver streams.

--- #6 Redirecting catalog cache misses to the local tablet ---
* Reads ride the Perform RPC; catalog reads flagged kCatalog via
  is_ysql_catalog_table; they hit master only because the catalog table's sole
  tablet is kSysCatalogTabletId (replicas == masters). No explicit route-to-master
  branch.
* BEST chokepoint: PgClientSessionImpl::DoPerform (where the response cache already
  short-circuits master reads). Serve from the local tablet when its safe time >=
  required read time / catalog version; else fall through to master.
* Hazards to honor:
  - Catalog reads pin a master-leader-chosen read time for read-your-writes
    (catalog_read_time_). A lagging local copy violates this -> must validate local
    safe time >= pinned read time / required version, with master fallback.
  - Sys-catalog reads disable read-restarts (global_limit = read) -> the local
    serve must preserve that.
  - DDL read-your-writes within a session: only redirect pure reads not inside a
    txn that has written to sys_catalog (matches plan's note).
* TENTATIVE: redirect in DoPerform with a freshness check (local safe time/version
  vs required), master fallback, read-restart suppression preserved.

--- Top open questions to resolve in pass 2 ---
1. Bootstrap fetch without RAFT membership: can we reuse the remote_bootstrap file
   transfer service decoupled from config membership, or do we need a new RPC?
2. Filter vs. tolerate the non-PG sys.catalog metadata rows on tservers.
3. Generalizing the streamable-catalog-table set + DDL/schema-change + CREATE/DROP
   DATABASE handling in the poller.
4. CDC retention cost on master at scale (shared stream vs per-tserver), and the
   re-seed trigger when a tserver lags out of the window.
5. Heartbeat-path version gate (the async counterpart to the ReleaseObjectLocks
   gate).
6. Exact freshness predicate on the DoPerform redirect and the master-fallback path.

DECISIONS RECORDED (2026-06-19)
==================================================================
D1. BOOTSTRAP / RESEED = remote snapshot transfer (NOT consensus-driven RBS, NOT
    read-replica membership). Promoted to critical-path (reseed happens on every
    tserver add/replace/disk-loss, and whenever a tserver lags past the master's
    CDC WAL-retention window).
    - Mechanism: RemoteSnapshotTransferClient (remote_snapshot_transfer_client.h:52
      "source tablet does not necessarily have to be in the same RAFT group or even
      the same universe"), driven by the StartRemoteSnapshotTransfer RPC
      (ts_tablet_manager.cc:1832). Snapshot-only (no WAL:
      InitSnapshotTransferSession, remote_bootstrap_session.cc:122). Source side
      does NO membership check (CreateRemoteSession / FetchData,
      remote_bootstrap_service.cc). Built for "xCluster native bootstrap".
    - Fallback/alt: standalone RemoteBootstrapClient + override downloaded cmeta
      config with a single-peer local config (ConsensusMetadata::set_committed_config;
      precedent SysCatalogTable::SetupConfig). Heavier (brings WAL/cmeta) — prefer
      snapshot transfer.
    - Schema comes for free: the transferred superblock's KvStoreInfoPB.tables[]
      carries EVERY cotable schema (KvStoreInfo::ToPB iterates all tables,
      tablet_metadata.cc:733). No need for the initdb snapshot's
      exported_tablet_metadata_changes file.
    - Seed point composes with the poller: the snapshot is a RocksDB checkpoint at
      a well-defined committed OpId (last_logged_opid); start the CDC poller there.
    - Maturity: the transfer PRIMITIVE is production-shared with RBS (low risk); the
      xCluster orchestration that currently drives it is dormant/unmaintained
      (xcluster_bootstrap_helper.h:40) -> drive the low-level RPC ourselves.
    - Reseed is tombstone-then-replace (not in-place); our standalone driver
      controls the tombstone step.
D2. UPDATE = per-tserver poller of kSysCatalogTabletId using the xCluster RAW WAL
    format (NOT CDCSDK: logical/pgoutput is PG-protocol = unusable to repopulate a
    DocDB tablet; proto format is decoded = needs re-encoding). Apply via the
    xCluster external-intents / external-transactions path.
    - Local copy = a normal single-peer tablet (regular RocksDB + IntentsDB). It
      needs NO transaction participant and NO status tablet (external-apply is
      self-contained: the streamed APPLY record carries commit_ht).
    - IntentsDB IS required: intents stream eagerly pre-commit (same WAL); they
      can't become regular records until commit_ht is known, so they stage in the
      IntentsDB and move to regular on the APPLY record
      (PrepareApplyExternalIntents, rocksdb_writer.cc:1177).
    - 1->1 local-apply mode exists (xcluster_output_client.cc:511); cotable_ids
      pass through verbatim (we bootstrapped identical table_ids).
    - The one blocker: cdc_service.cc:1707 rejects non-CDCSDK streams on
      sys_catalog. Work = relax that guard + create an XCLUSTER stream on
      sys_catalog + checkpoint/retention wiring (SetCDCCheckpoint lacks xCluster).
    - Poll cadence: trigger an eager poll on the catalog-change notification
      (heartbeat / ReleaseObjectLocks are free "poll now" signals; no CDC
      push/long-poll exists), idle lazily otherwise.
D3. RBS-vs-Raft-observer settled in favor of CDC. (a) sys_catalog Raft config ==
    master set, bidirectionally -> 1000 tserver UUIDs corrupt master-identity;
    (b) every tserver add/remove is a config-change Raft op written INTO sys_catalog
    (churn -> write traffic on the replicated tablet); (c) 1000 Peer state machines
    + 1000 reactor timers + ~1000 status-only heartbeat RPCs/interval on the leader,
    not lazyable without new code. CDC's idle floor is lower (empty GetChanges is an
    O(1) index compare, no per-consumer server-side timer/state) and reducible to
    ~0 with triggered polls. Also: master sys_catalog WAL is genuinely silent when
    idle (every non-PG write gated on real state change; PB-equality +
    empty-batch skips, sys_catalog_writer.cc:109 / sys_catalog.cc:747).
D4. GATE: expose catalog version V to backends only when the LOCAL copy has applied
    everything for V. Two equivalent variants (same correctness + latency; both
    become true exactly when V's txn is applied locally). Requires in-order apply.
    RECOMMENDED = HT-watermark variant (keeps the poller catalog-agnostic):
      - Master sends a hybrid-time watermark in a NEW ReleaseObjectLocks field
        (e.g. catalog_data_hybrid_time) = the version-READ HT (already chosen in
        ReadWithRestarts, sys_catalog.cc:945; >= commit_HT(V); currently discarded,
        thread it out). Tserver waits XClusterPoller::GetSafeTime() >= that HT.
      - Wait on the POLLER's producer_safe_time_ (advanced only AFTER a batch is
        applied, xcluster_poller.cc:667), NOT the local tablet MVCC safe time:
        external writes set only the record's encoded write ts (external_hybrid_time,
        rocksdb_writer.cc:195), the op's MVCC time is the consumer clock -> different
        domain. So NOT TabletPeer::WaitForSafeTime(T) with producer-time T.
      - Propagate a HYBRID TIME, not a Raft OpId (OpIds are group-local; local copy
        is a separate group). And NOT the master's instantaneous safe-time/OpId at
        release (the APPLY lags commit, so master's own watermark is < commit_HT(V)
        then). For a TRANSACTIONAL stream the producer apply-safe-time IS
        ResolveIntents-gated (sound) -- earlier "loose LeaderSafeTime" caution was
        the non-transactional path.
      - apply_after_hybrid_time (tserver.proto:522) is a pure CLOCK wait
        (clock.cc:30) and load-bearing for acquire-ordering -> DON'T reuse; new field.
    ALTERNATIVE = applied-version variant: poller tracks applied
      pg_yb_catalog_version[db] (parses version-row writes), gate on >= V (analog of
      YbWaitForSharedCatalogVersionToCatchup, pg_yb_utils.c:1223). No new proto field
      (versions already in the message), but couples the poller to catalog semantics.
    Redirect freshness: read op carries an integer version, so for the DoPerform
      redirect rely on the gate (read at local apply safe time; gate guarantees
      backend sees V only after local has V), with the per-op version compare as an
      optional safety assertion. Maintaining both watermarks is cheap if desired.
    Baseline (both variants): wait for the master's APPLY/commit record to stream,
      then apply. Master-signaled eager local-apply = DEFERRED optimization (prior
      art: xcluster_external_apply_bootstrap-test.cc:315). Gap is real (catalog DDL
      is distributed; master reads V via read-through-intents before the APPLY is in
      WAL, transaction_status_cache.cc:204) but the wait gate handles it soundly.
    The inval-row write_time anchor is UNNECESSARY (read-HT is simpler/available).

PASS 2 RESOLUTIONS (2026-06-19) — the earlier "Top open questions" answered
==================================================================
R1 (bootstrap without RAFT membership): RESOLVED. RemoteSnapshotTransferClient is
   purpose-built for cross-RAFT-group/cross-universe transfer; source does no
   membership check. Schemas ride in the superblock. See D1 +
   learning-reseed-and-cross-raft-bootstrap.md.
R2 (filter vs tolerate non-PG sys.catalog rows): raw stream has NO per-cotable
   filter (only a sequences_data special case), so we receive the whole tablet incl.
   the non-PG sys.catalog metadata rows (primary table, cotable_id=nil). Harmless to
   apply (correctness fine), just wasted space. Filtering to PG cotables = small new
   producer-side check on the DocKey cotable_id prefix. DECISION: tolerate for now;
   filter later if space matters.
R3 (schema / new-cotable / CREATE-DROP DATABASE): RESOLVED. Raw stream carries
   CHANGE_METADATA_OP; WAL order guarantees schema-before-rows. New consumer
   component = replay CHANGE_METADATA verbatim into local RaftGroupMetadata
   (AddTable/AlterSchema/AddMultipleTables/RemoveTable), bypassing the stock
   consumer's remap (which ignores CREATE/DROP DATABASE). This is the one
   substantive new consumer piece; bounded.
R4 (retention cost + re-seed trigger): RESOLVED. Per-stream cdc_state; WAL bounded
   by 24h cap + 4h sys_catalog staleness reset (laggards self-evict and re-seed).
   Re-seed signal = CHECKPOINT_TOO_OLD on GetChanges -> snapshot transfer. Idle poll
   must stay < 4h staleness window (empty polls cheap, re-stamp checkpoint).
R5 (heartbeat-path gate): RESOLVED. CLAMP min(master_reported, local_applied) per db
   in the SetYsqlDBCatalogVersions wrapper (NOT defer the shm write — that fights
   the monotonicity/staleness-FATAL machinery). Clamp kTemplate1Oid (global) too.
R6 (redirect freshness predicate): RESOLVED. Per-op version on
   PgsqlReadRequestPB.ysql_db_catalog_version (field 36) + ysql_db_oid (37). Serve
   locally iff local_applied[db] >= op version, else skip redirect (normal master
   route; no new fallback). One in-memory local_applied_version[db] map (poller-
   maintained) serves the ReleaseObjectLocks wait, the heartbeat clamp, and this.

== THE ONE KEY NEW-CODE ITEM ==
Raw (xCluster) format is blocked on sys_catalog by cdc_service.cc:1707 (only CDCSDK
allowed there today; CDCSDK emits the unusable logical format). Enabling Option B =
lift that guard + create an XCLUSTER-source_type stream on kSysCatalogTabletId +
wire its checkpoint/retention. Retention/staleness/cdc_state machinery is shared and
works once the guard allows the stream type.
